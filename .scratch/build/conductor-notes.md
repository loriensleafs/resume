# Conductor notes for `/brain:build auto`

The working method and the carry-forward notes of the conductor session that ran `/brain:build auto` on 2026-10-27 (decision record rows 149 to 159). A new conductor reads this file with [STATUS](../../docs/STATUS.md). The decisions themselves live in the [decision record](../../docs/design/interview-2026-10-26.md) and in [build decisions](../../docs/design/build-decisions.md); this file only says how to run the next lanes and what each later task must remember.

## How the run works

1. **Lanes (rows 150, 164 and 177).** Up to 7 tasks build at once (row 177; it was 4), each in its own git worktree (the Agent tool's `isolation: "worktree"`), when their blockers are done and their files do not overlap. A worktree starts from GitHub's `main`, so the brief tells the builder to run `git merge --ff-only main` first. A worktree's `node_modules` is a symbolic link to the main checkout's folder: the builder runs `unlink node_modules` and `bun install` before anything else, so no install writes into the main checkout. The builder copies `private.yaml` in and never stages it.
2. **Builder brief.** Each builder writes its full report to a file in the conductor's scratchpad (`reports/<task>.md`) and replies in at most five lines: the commit, the test counts, the path, and any question for Peter (Peter's rule: findings land in files). The rest of the brief: The plain-talk block at the top; the task's body; the spec to read in full; the skills to load (the brain skills, the library skills through `bun run intent load`, the design-system skills and one real `resolve_version` call for UI work); Peter's standing rule ("the best option, not the easiest or the fastest, even when it means more work"); stage by name; never edit `tasks/todo.md` or `docs/STATUS.md`; one commit ending with the attribution line; no push (except a spike task, which pushes its prototype branch under row 151 after both release checks); questions come back in the report.
3. **Review (rows 149, 162 and 163).** After each task, reviewers run in parallel on a different model from the builders (Sonnet), each with [review-brief.md](review-brief.md) and its axis file in [axes/](axes/), and each writes its report to a file. A task that changes code gets four: correctness, security, architecture, and one reviewer for readability and performance together (it reads both `axes/readability.md` and `axes/performance.md`). A docs-only task or a deletion gets two: correctness and architecture. An agent-file task (`AGENTS.md`, repo skills, agent settings) gets three: correctness, architecture and security. A spike task gets three: correctness, security, architecture. A fix to security code still gets one extra security check.
   **How:** the conductor starts one review agent per task (Sonnet, with [review-agent-brief.md](review-agent-brief.md)), with a short prompt: the task id and title, its kind (code, docs or deletion, agent files, spike, or security fix check), the worktree, the diff command, the spec and task body, the points to judge, the library skills and docs-server need, and the review folder in the scratchpad (`reviews/<task>/`). The review agent starts the reviewers itself (a nested sub-agent works; tested 2026-10-27), checks each report's capability line, and merges the reports by [merge-brief.md](merge-brief.md). Each reviewer replies to it in one line.
4. **Fixes.** The review agent writes `decisions.md` in the review folder: one row per finding with a proposed decision and its reason, and replies to the conductor in two sentences. The conductor reads only `decisions.md` (a report file only when a row is unclear), confirms or changes each proposed decision, decides every finding that is not Peter's (the best option, recorded in [build decisions](../../docs/design/build-decisions.md) when worth his look), and sends the fix list to the same builder through SendMessage. A builder whose run the harness stops twice is replaced by a fresh agent with the state and the remaining steps.
4a. **Workflow (row 165).** Peter opted in to workflows. Run each task as one run of [build-task.workflow.js](build-task.workflow.js) with `scriptPath` and `args` `{ id, title, kind, builderPrompt, spec, libraries, docsServer, reviewPoints, reviewFolder }`: the builder in its own worktree (it returns its worktree, base, tip, report path, test counts and questions as structured output), then the tiered reviewers in parallel (each returns its report path and its capability line; a report without the skills on its first line runs once more), then one merge agent that writes `decisions.md` by [merge-brief.md](merge-brief.md). One run per task, so each task returns as soon as it is done; start up to 4 runs at once (row 164). The run returns `{ id, build, reviews, missing, merge }`; read `decisions.md`, decide, then start one fix agent with the Agent tool that works inside the builder's worktree path (the worktree stays, because it has commits) with the fix list and the builder's report path. To review a build again, pass its build result as `args.build`: the build is skipped. A run that misbehaves is stopped with TaskStop and resumed with `resumeFromRunId` after a fix. Every builder reads [builder-brief.md](builder-brief.md); its prompt adds the plain-talk block, the task, the spec, the skills and the carry-forward lines.
   **Found on the first run (D6, 2026-10-27):** a workflow agent has no Agent tool, so the first script's review agent could not start reviewers and reviewed both axes alone. The script now starts the reviewers itself; [review-agent-brief.md](review-agent-brief.md) serves only a review started with the Agent tool outside a workflow. The build half (worktree, commit, structured result) worked as written.
5. **Merge.** `git merge --no-ff` with a message that says what the review changed; then `bun install` if packages changed, `bun run build` and `bun test` on `main`. Security code that guards pushes gets one extra security check after its fixes.
6. **Stops (rows 152 and 154).** The run stops for Peter only for a set-up item only he can do (a key, a secret, an account, a paid service, a check in his own browser), source work (task 13's interviews, any change to an approved source such as K11 to K13), a critical review finding that needs his decision, and the approvals row 151 keeps (force-push, visibility, a deploy by hand, money such as an eval run, a new dependency, an approved source, `scripts/docs-only.txt`). Checkpoint reviews do not stop the run. Wordings are drafted per task (row 153).
7. **Never** write a value from `private.yaml` anywhere; a reviewer once quoted it from a failing test's output, and the brief now forbids it.
8. **Pushes.** Push through the `release` skill once every 2 or 3 merges, or at a drain, not after every merge; each push re-runs the before-commit checks.
9. **Drain and restart.** When the conductor's context grows large, it starts no new task, merges the lanes in flight, rewrites STATUS, pushes, and Peter runs `/clear` and `/brain:build auto`.
